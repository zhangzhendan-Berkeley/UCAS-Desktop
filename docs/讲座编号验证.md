# 讲座排课编号：已验证内容与缺失条件

## 目前结论

`courseSchedId` 按记录创建或导入批次递增是一种可能解释，尚未证实。本人课表只读取样中，同一课程相邻周的增量不固定；同一天不同场次的编号可以相差数万，上课更早的编号也可能更大。因此，“按导入先后分配”即使成立，也不能据讲座的上课日期推出其导入时间或一个可靠的小编号区间。

本次进一步检查日课表返回字段，发现 `courseType`、`courseSchedType`，但没有创建/导入时间。没有真实讲座的对应样本及类型取值定义，不能把某个数字类型直接认定为讲座，也不能凭七位编号的外形判断。

## 为什么暂未实现邻近编号枚举

枚举的前提是有一个只读核验入口：输入候选 `courseSchedId`，返回其讲座名称、场次日期和类型。本次查阅以下公开客户端及接口资料，已见的相关接口主要是本人按日/按周课表、我的课程、时间戳和签到；未找到可只读核验任意排课编号的接口。这是本次调查范围内的结论，不代表服务器绝无此能力。

`stu_scan_sign.action` 即使使用 GET 也会实际提交签到，不作为试号或判断“是不是讲座”的探针。系统编号位于两套平台：选课系统的讲座编号不能直接替换轻新课堂排课编号。

## 可靠的识别依据

- 在本人课表中找到该编号，并核对课程/讲座名称与完整起止时间。
- 已知来源的真实讲座二维码与官方场次对应关系。
- 将来找到有文档或已验证的只读场次详情接口，返回上述信息后再作小范围核验。

如果获得数场真实讲座的二维码，可对比同一场不同时间、同一天不同场次，以及不同日期的样本。仅证明编号相近仍不足以证明生成规则，更不能承诺可稳定推算下一场。
